你的理解主线是对的，但当前实现不是“所有硬约束都最后才由 Verifier 排除”，也不是 Beam Search。它是一个**分层筛选 + 小规模组合枚举 + finalist 真实路线复核**的规划器。

## 当前完整规划过程

```
NormalizedConstraints
  ↓
天气事实 → Catalog 单资源筛选
  ↓
构造 PlanningIntent 与候选骨架
  ↓
按角色建立候选池、枚举组合、做本地估算评分
  ↓
挑出受预算限制的 finalist
  ↓
高德/Route Provider 逐段重建路线与时间线
  ↓
Availability Provider 批量检查
  ↓
Verifier 整单复核 → 有界局部修复
  ↓
固定策略重排 + 多样化 Top 3
  ↓
CandidateSet → Presenter/API → 前端
```

### 1. Enrichment 交给 Planner 的输入

Planner 收到的是 `NormalizedConstraints`，其中已经有：

```
日期、时间窗、时长、出发地坐标、同行人、预算、距离、
偏好、饮食标签、场景标签、避开项、严格预算、
最晚到家、全程距离
```

它要求至少有：`date + time_window + location`，否则不能规划。

### 2. 先拿天气，但天气目前是“组合前剪枝”

Planner 一开始会调用天气 Provider。

如果天气不利，就从 Catalog 候选中先移除“天气敏感的活动类 POI”，例如明显依赖户外的活动。它现在不是由 Verifier 在最后判定，而是先减少不合适的组合。

这是有效率的做法，但也意味着当前天气模型较简单：主要是“恶劣天气下，不选天气敏感活动”，还不是完整气象风险评分。

### 3. Catalog 在骨架之前召回并做单 POI 初筛

你说“按每个站点召回”基本正确，但实际上顺序是：

```
Catalog.recall(constraints)
→ 得到统一候选全集
→ 再按骨架角色切成不同候选池
```

Catalog 会先做单资源级别的硬筛选/告警，例如：

- 严格预算下，单个 POI 明显超预算；
- 明确不支持儿童或儿童年龄不符合；
- 与出发地直线距离已经明显超限；
- 基础营业信息不匹配时段；
- 数据缺失时保留 warning。

因此，Verifier 不需要再次处理所有静态事实。

### 4. 规划骨架不是只由时间窗口决定

当前有四个显式骨架：

```
2 站：活动 → 泛餐食
3 站：午餐 → 活动 → 晚餐
3 站：活动 → 休息/咖啡 → 晚餐
4 站：活动 → 午餐 → 活动 → 晚餐
```

骨架选择同时看：

- 时间窗是否覆盖午餐、晚餐、下午茶；
- 总可用时长是否至少 5/6/8 小时；
- 用户节奏偏好：
  - “轻松、松弛、不赶” → 最多 2 站；
  - “丰富、充实、多玩几个” → 最多 4 站；
  - 其他 → 最多 4 站。

但注意：当前**永远先包含 2 站的“活动 → 泛餐食”骨架**。所以同一时间窗下，可能既有两站方案，也可能有三站方案；不是“时间一确定，就唯一确定站数”。

### 5. 按骨架角色建立候选池

例如三站骨架：

```
午餐 → 活动 → 晚餐
```

会建立：

```
午餐池：餐厅
活动池：活动
晚餐池：餐厅
```

每个角色只接收允许的资源类型。

对 3/4 站骨架，当前会先把每个角色的候选按偏好、场景、饮食、避开项、预算倾向和距出发地距离预排序，限制到最多 `8` 个，以控制组合爆炸。

对 2 站骨架，目前没有同样严格的 Top-K 截断。

### 6. 枚举组合，不是 Beam Search

当前就是笛卡尔积：

```
午餐候选 × 活动候选 × 晚餐候选
```

逐个形成具体站点顺序的候选方案。

所以它是“小规模、受上限的穷举组合”，不是“一层层只保留前 K 条路径”的 Beam Search。

每一个组合先用本地直线距离和时间估算，过滤：

- 预计总时长超时间窗 / 指定时长；
- 单段估算距离超限；
- 指定全程距离超限；
- 有返程要求时，预计无法按时回家；
- 严格预算超限。

剩下的方案才进入评分。

### 7. 本地初评分

每个可行组合会得到一个初步 `Plan` 和 `score_breakdown`。评分包括：

```
Catalog 基础可行性
骨架匹配
时长贴合
本地估算通勤
偏好 / 饮食 / 场景标签匹配
避开项惩罚
非严格预算倾向
```

这一步的路线仍是本地估算，不能当成最终路线事实。

### 8. 高德路线在哪里调用

高德不是在召回阶段，也不是对全部排列组合调用。

系统会先从初评分方案中选取一批 finalist，并限制总共最多验证 `24` 条路线段，避免 API 配额被长骨架耗尽。

然后对每个 finalist：

```
出发地 → 第 1 站
第 1 站 → 第 2 站
...
最后一站 → 出发地（只有用户要求最晚到家时）
```

逐段调用 `RouteProvider`。

- 配置高德时：可得到高德实际路线、距离、时长和 geometry；
- 未配置或失败时：走 Local/Replay/Mock 降级，并在结果中标识。

路线回来后，系统会按真实行程重新计算每一站的到店与离开时间，得到真正的时间线。

### 9. Availability 与 Verifier

路线时间线重建之后，才按“某个 POI 在某时间段”批量查询 Availability。

之后 Verifier 判断整单是否真的成立：

```
时间窗、指定时长、单段距离、全程距离、
返程存在且按时到家、餐时锚点、完整营业区间、
已确认不可用的动态状态
```

失败时：

- 可归因到一站的问题：最多两轮、同骨架单站替换；
- 无法可靠归因的整体问题：换下一个 finalist；
- 不会无限重试。

### 10. 返回 Top 3 前还会做两件事

首先，给已验证方案追加固定策略：

```
balanced / low_cost / low_travel / experience /
family_safe / weather_safe
```

这些不是重新生成方案，而是对可行方案按策略权重再排序。

然后会做多样化选择：避免三个方案只是换一家类似餐厅。它比较 POI 重叠、价格差异和路线差异，最终返回最多三条差异足够大的方案。

## 完整方案的数据结构

有，定义在 [planning.py](E:\\04_Develop\\Projects\\PycharmProjects\\happyFreeTime\\app\\domain\\planning.py)。

核心 `Plan` 大致是：

```
Plan
├─ plan_id
├─ composition_fingerprint
├─ skeleton_id
├─ title
├─ strategy
├─ total_score
├─ total_price / price_status
├─ total_duration_minutes
├─ stops[]
│  ├─ resource_id / name / type / role
│  ├─ start / end / duration
│  ├─ price / price_kind
│  ├─ tags / image / source
├─ route_legs[]
│  ├─ 起点、终点、起止时间
│  ├─ 交通方式、距离、时长
│  ├─ 高德或降级来源、缓存/降级状态
│  └─ geometry（前端地图画线）
├─ score_breakdown[]
├─ highlights[]
└─ tradeoffs[]
```

`CandidateSet` 还会包含：

```
plans
provider_facts（天气、地理编码、可用性）
warnings
catalog_warnings
conflict（若无可行方案）
```

所以最终输出绝不是“骨架 + 两三个 POI”；路线、时间线、价格状态、评分依据、事实来源和 warning 都已是结构化数据。

## 这部分是否适合改成 Agent？

适合，但不适合把当前 Planner 替换成“LLM 自由选 POI”。

更好的目标是：

> **LLM 负责规划策略与语义取舍；确定性 Planner 负责受控搜索；Provider 提供事实；Verifier 拥有最终否决权。**

我建议分三层让 LLM 参与。

### A. LLM 生成受约束的 Planning Guidance

在 Planner 前，LLM 根据用户偏好产出受控策略，而不是直接出方案：

```
{
  "pace": "relaxed",
  "allowed_skeletons": [
    "activity-meal-v1",
    "activity-break-dinner-v1"
  ],
  "preferred_roles": ["activity", "dinner"],
  "soft_priority": ["indoor", "novelty", "low_travel"],
  "tradeoff": "允许稍高预算，优先雨天可行和体验感"
}
```

Harness 负责检查：

- 只能选择已注册骨架；
- 不能绕过时间、预算、儿童、营业等硬约束；
- 不能凭空增加路线或 POI。

这能改善“骨架与固定权重太死”的问题，同时保留 `PlanningService.plan(...)` 的稳定接口。

### B. LLM 做“已验证候选的受限语义重排”

让 LLM 只看 5–12 个已经通过 Verifier 的候选，而不是让它从全世界选店。

它可以输出：

```
{
  "candidate_id": "plan_x",
  "semantic_delta": 3,
  "evidence": [
    "更符合‘带父母轻松聊天’而非单纯打卡",
    "对雨天与少走路的取舍更符合本轮表达"
  ]
}
```

约束：

- 只能对已有、已验证候选打小幅分；
- 必须引用 `Plan` / `Stop` / `ScoreContribution` 中已有事实；
- 不得让失败方案复活；
- 分值影响设上限，例如 `-5 ~ +5`；
- 仍由多样化模块选 Top 3。

这比让 LLM 直接决定所有评分更可靠，也能真正弥补“标签匹配难理解完整语义”的缺点。

### C. LLM 解释，但只解释事实

这是最安全、最适合第一步落地的能力。

Presenter 当前更偏模板化解释；可以让 LLM 基于已验证的 `Plan`、路线、评分和 warning 生成：

- 为什么这是首选；
- 相比另两条方案牺牲了什么；
- 为什么雨天仍可行；
- 哪个站最值得替换；
- “若预算增加 30 元，会有什么变化”。

但它必须只能引用输入中的事实，不能生成“这家评分 4.8、排队 10 分钟”这种不存在的内容。

------

## 最优演进方案

我不建议“一次性 Planner Agent 化”。推荐：

```
现在的可信 Planner / Verifier 保留
  ↓
先补 TemporalConstraint 与语义抽取可靠性
  ↓
加入 LLM Planning Guidance（受限骨架与软目标）
  ↓
加入已验证候选的受限语义重排
  ↓
最后加入 grounded explanation
```

这样最终可以很准确地讲成：

> 模型不直接生成行程，而是生成受约束的规划策略并在已验证候选间进行语义权衡；确定性搜索、外部事实校验和 Verifier 保证所有输出方案满足可执行约束。

这比“让 LLM 选几个 POI 再让规则兜底”更强，也更符合你项目当前的可信规划优势。
