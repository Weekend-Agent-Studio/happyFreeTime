## 🎯 一句话原则

测试通过只能证明：**在测试实际经过的边界内，给定这些输入和替身数据，代码满足了写下来的断言。**

它不能自动证明断言没遗漏、外部数据真实、真实模型准确、推荐符合主观偏好，或浏览器中的完整用户旅程可用。判断一个测试是否有说服力，先问四件事：

1. 输入是真实数据、固定样例，还是测试替身？
2. 实际经过了哪些模块，绕过了哪些模块？
3. 断言检查了什么结果，遗漏了什么结果？
4. 失败时能否快速定位到具体层？

## 🔧 `unittest discover` 命令

```powershell
python -m unittest discover -s tests -v
```

| 部分 | 含义 |
| --- | --- |
| `python -m unittest` | 用当前 Python 解释器运行标准库 `unittest` 模块 |
| `discover` | 自动发现测试，而不是逐个指定测试模块 |
| `-s tests` | 从 `tests` 目录开始发现 |
| 默认 `test*.py` | 只导入符合该文件名模式的模块 |
| `-v` | 详细列出每条测试及其结果 |

被导入的模块中，通常只有 `unittest.TestCase` 子类里以 `test` 开头的方法会作为测试执行。因此它不是无条件运行 `tests` 目录下的所有 Python 语句；不过导入模块时的顶层代码仍会执行，所以测试文件应避免有副作用的顶层逻辑。

## 📚 常见测试层次与证据边界

| 类型 | 典型边界 | 优点 | 主要不能证明 | 本项目例子 |
| --- | --- | --- | --- | --- |
| 单元测试 | 一个函数或 Service | 快、稳定、定位清楚 | 模块组合和真实依赖 | Enrichment、Gate、Planning 测试 |
| 集成测试 | 多个真实模块协作 | 能发现契约和状态衔接问题 | 完整浏览器旅程 | Entry Graph、Repository 测试 |
| API 测试 | HTTP 契约到后端业务层 | 验证状态码、响应和落库 | React 渲染、URL、浏览器刷新 | `tests/test_api.py` |
| React 组件测试 | 组件和前端状态流 | 快速验证渲染、交互和异常分支 | 真实浏览器导航、真实后端和数据库 | 当前尚未建立 |
| 浏览器 E2E | 浏览器、前端、API、数据库 | 最接近真实用户旅程 | 大量边界组合；定位较慢 | 已做一次工具驱动的本地主路径回归，自动化文件待建立 |
| Smoke 测试 | 一小组关键路径 | 快速发现系统是否明显损坏 | 完整覆盖和深层质量 | `evals/smoke_cases.json` |
| 离线 Eval | 固定数据集与质量指标 | 可比较模型或策略版本 | 开放世界的全部输入 | Router 准确率与推荐质量尚未建立 |

“测试金字塔”通常意味着底层单元测试多而快，上层 E2E 少而关键。它不是要求固定比例，而是避免所有问题都依赖昂贵、慢且难定位的浏览器测试。

## ⚡ 为什么叫 Smoke Eval

Smoke test 是范围浅、运行快、覆盖关键路径的健康检查，用来尽早发现系统是否已经明显不可用。名字来自“先看设备通电后是否冒烟”的比喻；它不等于端到端，也不等于完整回归。

本项目的 5 条用例保存在 [`evals/smoke_cases.json`](../../evals/smoke_cases.json)：

1. 缺失信息时使用默认值并生成方案
2. 严格预算但缺金额时反问
3. 显式日期无法解析时反问
4. 显式地点无法解析时反问
5. 严格低预算导致结构化冲突

[`app/evaluation/smoke.py`](../../app/evaluation/smoke.py) 直接构造 `Interpretation`，只运行：

```text
Interpretation -> Enrichment -> Gate -> Planning
```

因此它绕过 Router、LangGraph、HTTP、SQLite 和 React。它验证的是离线业务行为，不验证真实语义抽取，不验证 Graph 状态，也不是浏览器端到端测试。用例主要断言结果种类、反问字段、冲突代码和是否存在方案，没有评价推荐排序或主观质量。

## 📊 真实 LLM 抽取准确率如何评测

现有 [`tests/test_router_extractor.py`](../../tests/test_router_extractor.py) 使用预置的结构化结果和异常，能证明：

- Router 能接收结构化输出
- 模型失败后只重试一次
- 再次失败会降级为 `CLARIFY`

它不能证明模型从自然语言中提取正确。要评价真实模型，应建立带人工期望答案的数据集，并按固定版本重复运行。常用指标如下：

| 指标 | 回答的问题 | 注意点 |
| --- | --- | --- |
| Schema validity | 输出是否始终符合 Pydantic 契约 | 只说明格式合法，不说明语义正确 |
| Intent accuracy | 意图分类有多少正确 | 适合互斥类别 |
| 字段 Precision | 模型提取的字段里有多少是真的 | 防止凭空补约束 |
| 字段 Recall | 应提取的字段里有多少被找到 | 防止漏掉用户要求 |
| 字段 F1 | Precision 与 Recall 的综合 | 适合多字段比较版本 |
| Exact match | 整条结构是否完全正确 | 很严格，适合作为高标准辅指标 |
| 关键字段错误率 | 日期、预算、人数等高风险字段错多少 | 比平均准确率更贴近业务风险 |
| 稳定性 | 同一输入多次运行是否一致 | LLM 输出可能非确定 |
| 延迟与成本 | 达到质量需要付出多少 | 质量提升不能脱离工程约束 |

模糊表达可能有多个合理答案，不能机械地把唯一字符串当真值。应先定义标注规则，对分歧样例进行人工复核，并区分“允许默认”“必须澄清”和“可以安全推断”。

推荐质量是另一套评测，不能被抽取准确率替代。可逐步检查硬约束满足率、无解识别率、候选多样性、排序相关性、解释忠实度，以及最终用户选择或修改行为。

## 🌐 Playwright 与刷新回归

Playwright 是浏览器自动化测试工具。它可以像真实用户一样打开页面、输入需求、点击按钮、等待方案、刷新网页，再检查消息和方案是否仍存在。

对“生成方案后刷新仍可恢复”，证据组合是：

| 层次 | 应验证的行为 |
| --- | --- |
| API 测试 | 已知 `session_id` 时，`GET session` 返回消息、方案和稳定会话状态 |
| React 组件测试 | 给定一个 `SessionView`，页面正确还原消息、约束和方案 |
| Playwright E2E | 提交规划后 URL 保存会话定位；真实刷新后，页面通过 API 恢复同一会话 |

当前 API 层和一次本地浏览器主路径已验证功能成立。React 组件测试适合作为快速回归，但不能单独证明刷新闭环，因为它通常会 Mock API，也不会覆盖真实 URL、浏览器导航、后端和 SQLite；因此还应将本轮步骤固化为可重复 Playwright 测试。

## 🧪 常见测试替身

| 名称 | 主要用途 | 本项目对应 |
| --- | --- | --- |
| Stub | 返回预设值，让被测代码继续运行 | 给 RouterExtractor 预置结构化结果 |
| Fake | 用简化但可工作的实现代替真实依赖 | Demo Router、内存 checkpoint |
| Mock | 验证依赖是否按预期被调用 | 可检查模型调用次数和重试次数 |
| Fixture | 为测试准备稳定的输入和环境 | Mock Catalog、临时 SQLite、smoke cases |

项目里的类名不一定严格遵守教科书分类。例如 `FakeStructuredModel` 同时提供预设结果并记录调用次数，既有 Fake/Stub 特征，也承担了部分 Spy 的用途。面试时解释它实际做什么，比死背名字更重要。

## 🎓 高频面试问答

### 单元测试和集成测试有什么区别？

单元测试隔离一个业务单元，强调速度、确定性和定位；集成测试让多个真实组件协作，重点发现契约、序列化、数据库或状态传递问题。边界比名称更重要，例如 Graph 测试虽然使用内存 checkpoint，仍然集成了 Router、Enrichment、Gate 和 Planning。

### 为什么不能只写 E2E？

E2E 接近用户，但运行慢、失败原因多、数据准备复杂。大量规则用单元测试精确覆盖，少数关键旅程用 E2E 兜底，能同时获得反馈速度和真实信心。

### 什么是回归测试？

把已经发现或修复的行为固化成自动断言，防止以后改动让旧问题重新出现。刷新恢复修好后，应同时保留 API、组件和一条浏览器主路径回归。

### 什么是 Flaky Test？

代码没有变化时，测试也会偶发成功或失败。常见原因是依赖真实时间、网络、随机数、共享数据库或不可靠的异步等待。治理方法是注入时钟、固定随机种子、隔离数据、使用确定条件等待，并减少非必要真实外部依赖。

### Mock 越多越好吗？

不是。Mock 能让测试快而稳定，但 Mock 的契约可能与真实依赖漂移。关键边界仍需契约测试或集成测试；对真实 LLM 和 Provider，还需要离线数据集和少量受控集成评测。

### 测试覆盖率高是否等于质量高？

不等于。覆盖率只说明代码被执行过，不说明断言有效，也不说明业务场景完整。更可靠的证据包括关键风险用例、分支与不变量断言、故障路径、变异测试，以及线上反馈。
