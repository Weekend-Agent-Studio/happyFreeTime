# 1006 去哪儿 AI 面试：问题还原与口述答案

> 根据 2026-10-06 的面试回忆整理。题目是依据关键词还原的练习版本，不代表面试官原话。重点是建立答题思路；项目例子可以帮助解释判断，不必把每个设计都说成已经上线。

## 先练哪几题

| 优先级 | 题目 | 为什么重要 |
| --- | --- | --- |
| P0 | 4–6：Agent 如何停止、如何判断进展 | 能区分“会调用工具”和“能控制系统” |
| P0 | 7–10：为什么重构、如何设计和解释评测 | 直接决定项目叙事是否可信 |
| P0 | 11–14：AI 开发如何对结果负责、切片如何验收 | 独立开发项目最容易被追问的地方 |
| P1 | 1–3：MCP 的价值、企业落地和底层机制 | 基础概念，但要避免把协议说成万能适配器 |
| P1 | 15–16：Redis 缓冲 MySQL、一致性与容量 | 通用后端系统设计，与你的项目关联较弱 |

**统一答题节奏：结论 → 机制 → 一个例子 → 边界。** 先用 30–60 秒回答；对方追问再展开。遇到记不清的实现，直接说“这里我会这样设计”，不要把设计建议冒充已完成的代码。

## 一、MCP：解决什么，不能解决什么

### 1. MCP 是为解决什么问题设计的？相比每个 Agent 自己接工具有什么优势？

**口述答案：** MCP 主要标准化 AI 应用与外部能力之间的接入方式。工具提供方以 MCP Server 暴露工具、资源或提示模板，AI 应用中的 MCP Client 按共同协议发现和调用它们。这样应用不必为每个工具提供方单独写一套发现、参数描述和调用适配；工具提供方也不必分别适配每个 AI 应用。所谓 `M×N → M+N` 是集成工作量的理想化表达，前提是两侧都遵守协议。它节省的是连接层重复劳动，不自动解决权限、数据口径和业务语义。

**考点：** 协议标准化的范围；MCP 与普通 function calling 的关系。

**记忆：** “**接得上**”是 MCP 的价值；“**用得对、用得安全**”仍由应用负责。

**追问一句：** 我项目当前更适合由 Harness 确定性调用路线、天气等 Provider，因为它们是规划的必需事实。以后需要让多个 AI 客户端复用这些能力时，可以在 Provider 外提供 MCP Server；无需为了使用工具而先引入 MCP。

### 2. 企业里有很多数据源，格式和权限都不一致。用了 MCP 就能直接接入吗？落地难点是什么？

**口述答案：** 不能。MCP 统一的是对客户端暴露能力的协议，企业仍要在 Server 内完成数据源适配。落地时我会先按业务能力定义少量稳定工具，例如 `query_order_status(order_id)`，再分别接数据库、内部 API 或文档系统，并统一返回字段和错误码。权限方面要把用户身份传到后端做租户隔离、最小权限和审计，不能因为模型看到了工具就默认它有权访问。还要处理数据新鲜度、分页、大结果截断、限流、超时以及敏感字段脱敏。

**考点：** 协议层与数据治理层的区别；统一接口不等于统一数据。

**记忆：** “**语义口径、身份权限、质量时效、运行治理**”四类问题。

**容易失分：** 把“接上 MCP”说成能自动理解所有数据库 Schema，或把工具描述当成访问控制。

### 3. 不同工具的参数、返回格式和权限都不同，MCP 底层如何适配？

**口述答案：** MCP 采用 Host–Client–Server 结构。Server 声明自己的能力和工具输入 Schema，Client 发现工具后，Host 决定把哪些能力提供给模型；模型提出工具名及参数，Host/Client 校验并发起调用，Server 再把请求翻译为自己的数据库查询或 API 调用。不同工具的数据格式不是由协议自动变成同一种业务模型，而是由各 Server 的实现映射为约定的输入和输出。授权由实际身份系统、Server 和应用策略执行；模型的选择只是调用提案。底层通信使用规范化消息与传输方式，但面试中更重要的是讲清“**协议负责调用合同，Adapter 负责转换，权限系统负责授权**”。

**考点：** Host/Client/Server、能力发现、Schema、Adapter、授权边界。

**记忆：** “**发现 → 提案 → 校验/授权 → 调用 → 标准结果**”。

**延伸追问：** 工具结果也可能包含恶意指令，所以应把它当数据，限制输出范围，并在高风险写操作前做服务端授权和用户确认。MCP 不会天然消除 prompt injection。

官方资料：[MCP Server primitives](https://modelcontextprotocol.io/specification/draft/server/index)、[MCP SDK 调用示例](https://ts.sdk.modelcontextprotocol.io/v2/clients/calling)、[MCP 授权说明](https://apps.extensions.modelcontextprotocol.io/api/documents/authorization.html)。协议版本会演进，面试时通常不必背某版握手字段。

## 二、Agent 死循环：停止条件与“真的在推进”

### 4. Agent 为什么会反复调用工具？你会设置哪些终止条件？

**口述答案：** 循环常见于目标不清、工具一直返回相同信息、错误被模型误读成“再试一次”，或者没有明确的完成判定。我会设置三层停止条件：第一层是硬预算，包括最大轮数、工具调用数、时间和费用；第二层是重复检测，同一工具、规范化参数、相同状态和相近结果反复出现时停止；第三层是业务终止，成功满足目标、确认不可解、需要用户补信息、权限不足或外部系统持续失败时结束。停止后要给出明确结果和原因，而不是无限重试或假装成功。

**考点：** 技术预算与业务停止语义的区别。

**记忆：** “**预算封顶、重复拦截、业务收口**”。

### 5. 你说对工具调用做哈希。参数略有变化时，怎样判断任务真的在推进？

**口述答案：** 哈希只能发现完全重复，不能证明进展。我会先为任务定义可观察的状态和完成条件，再看一次调用有没有产生“有效状态变化”。例如查资料任务看新增了多少独立且相关的证据；排路线任务看候选是否由无解变可行、冲突数是否下降；代码修复任务看目标测试是否从失败变通过。再记录每步的工具、输入、输出摘要、状态差异和下一步假设。如果连续几步没有新增信息或约束改善，就停止、换策略或向用户反问。判断标准由任务定义，不能用一个通用哈希代替。

**考点：** progress metric、状态差异、局部最优与重复调用。

**记忆：** “**先定义终点，再定义每一步的可观察增量**”。

### 6. 如果 Agent 连续失败，你如何区分“值得再试”与“应该停止”？

**口述答案：** 我会按错误类型处理。短暂网络超时可以有限重试并退避；参数格式错误只允许修正后重试；同一参数触发相同业务错误时再试通常没有价值；权限拒绝、硬约束冲突或候选耗尽应直接终止或反问。重试必须改变某个可解释的变量，并且消耗统一预算。比如行程候选因餐厅停业失败，可以尝试替换餐厅；如果预算和营业条件共同证明无解，就返回冲突，不再让模型继续碰运气。

**考点：** 错误分类、幂等性、重试预算、终止原因。

**记忆：** “**瞬时故障可重试；确定性失败换策略；无可行策略就停止**”。

## 三、项目架构：为什么从 Multi-Agent/ReAct 转向受约束流程

### 7. 你把多 Agent/ReAct 改成“模型 + 确定性 Harness”，依据是什么？

**口述答案：** 我先按决策性质拆任务。用户说“浪漫、不累、有新鲜感”，这类开放语义适合模型；路线距离、营业时间、预算上限、版本状态和是否执行修改，可以由程序和 Provider 验证。早期多 Agent 原型把必需的事实获取、方案生成和校验都放在模型循环里，阶段交接多，失败也难定位。于是我让模型提出意图、软目标和有限结构，代码负责工具调用、候选搜索、排程和最终校验。这个方向既来自具体失败模式，也做了共同任务对照：在 16 条人工复核任务、两次重复运行中，Completed V1 为 13/16，V2 为 16/16；P50 约从 10 秒降至 5.5 秒，P95 约从 24–25 秒降至 7 秒。这个对照说明整体版本效果更好，不能把全部增益归因于单个模块。

**考点：** 职责划分的依据，以及定性案例与定量证据如何结合。

**记忆：** “**语义给模型，事实与不变量给程序；反例促重构，对照看效果**”。

### 8. 这 16 条共同任务怎么设计？能保证覆盖普通用户吗？

**口述答案：** 我先按高风险行为分层设计共同集：5 条完整规划、5 条缺字段、3 条硬冲突、3 条复合语义。每条在运行前人工确定预期结果，用相同输入和判定口径跑两个冻结版本，每个版本重复两次；同时固定时钟、地点和必要 Provider 条件，减少环境差异。它能检验这些能力切面，尤其是旧版稳定失败的冲突判断。16 条样本太小，而且是设计出来的任务集，不能声称代表所有真实用户或生产成功率。若要证明用户分布覆盖，我会再收集匿名真实会话，按意图和失败类型抽样，保留未见过的盲测集并持续监测线上分布漂移。

**考点：** 分层覆盖、事先标注、共同 Oracle、可复现性、外部有效性。

**记忆：** “**覆盖关键风险，不代表真实分布**”。

**追问准备：** 这组共同任务中的 5 条“缺字段”两套系统都使用默认值，没有真正触发反问，所以不能拿它证明多轮恢复优势。修改方案也未纳入这组共同集，需要引用独立评测。

### 9. 固化流程后，是否发现规则不够、又把决策交回模型？举一个真实例子。

**口述答案：** 有。最初确定性 PlanningIntent 对“带父母想有新鲜感但别太累”“安静约会想慢慢聊天”主要靠有限关键词，容易遗漏复合软目标。我没有把路线、时间和硬约束再交给模型，而是让模型在可校验的范围内提出软目标、站点结构和按角色的检索表达。模型提案经 Compiler 校验；检索仍先做 Catalog 硬过滤，最后由 Planner 和 Verifier 决定可行性。另一个反例是“清淡晚饭”：模型能理解“清淡”，但规则召回缺少 POI 语义证据，因此引入 Hybrid Retrieval。在 36 条冻结任务上，Rule Intent + Rule Retrieval 为 34/36，Rule Intent + Hybrid 为 36/36；这说明问题发生在召回证据层，而不是要把最终方案交给模型自由生成。

**考点：** 固定流程的适用边界；局部恢复模型决策；组件消融。

**记忆：** “**哪一层丢了语义，就只在那一层增加模型能力**”。

### 10. 既然模型更灵活，为什么不让它直接规划、直接调用所有工具？

**口述答案：** 直接生成可以很快得到看似合理的行程，但本项目需要满足可验证的地点、营业、路线、时间和预算约束。模型可以提出方案结构，但不能凭文本保证餐厅营业或路线可达。因此模型负责开放语义和有限提案，Provider 给事实，Planner 排时间线，Verifier 独立裁决；失败时有明确冲突和安全回退。这种设计牺牲了一部分自由度，换来可重放、可测试和可解释的失败。若未来有新的语义能力缺口，我会先用案例和消融证明收益，再扩大模型决策权。

**考点：** 自治程度与可验证性之间的取舍。

**记忆：** “**模型提案，系统核验，用户看到的是核验后的结果**”。

## 四、AI 生成代码：怎样保证质量和对结果负责

### 11. 长期用 AI 全栈开发，怎么避免代码越来越难维护？

**口述答案：** 我把 AI 当执行和讨论伙伴，架构决策与验收责任由我承担。开始一个切片前先定义用户行为、模块职责、允许改动范围和退出条件；实现时保持领域契约清晰，不为单个样例堆分支；提交前看 diff，检查新增抽象有没有真实调用方、是否复制了旧逻辑、是否破坏已有路径。对于跨模块变化，我让每个切片独立提交和回归，再用冻结评测看用户行为是否退化。技能或提示词可以帮助发现遗漏，但不能代替代码审查和运行证据。

**考点：** AI 辅助开发的责任归属、架构控制、可维护性。

**记忆：** “**先定合同 → 小步实现 → 审 diff → 验行为 → 留证据**”。

### 12. 单个开发切片的测试，你和 AI 是怎么设计并执行的？

**口述答案：** 我先把切片目标写成可观察行为，再按风险分层测试。例如修“早上出发”时，先列正反例：“早上出发”只约束出发、“早上出去玩”约束整体时段、“九点出发”给精确时间；然后做 Compiler 的确定性单测，再做 Graph 级创建、补约束、反问恢复测试。涉及外部模型时，先用固定提案测试系统逻辑，再用少量真实模型案例检查提案质量；发布前跑同一份 Frozen 集，最后只对关键用户旅程做浏览器验证。失败要分清代码回归、模型波动、Provider 环境和评测真值问题，不能靠反复重跑直到通过。

**考点：** 从需求派生测试、测试金字塔、确定性与实时评测分离。

**记忆：** “**一条切片 = 行为例子 + 失败反例 + 所属层测试 + 回归门槛**”。

### 13. AI 完成需求分析、前后端开发、模型选型和链路打通，你如何对最终结果负责？

**口述答案：** 对结果负责，意思是我能定义“什么算成功”，也能在失败时定位并修正，而不是只展示一个能运行的 Demo。需求阶段确认用户任务、边界和异常路径；设计阶段定数据合同与谁有最终裁决权；开发阶段按切片做接口和回归；集成阶段用真实用户旅程检查从输入到持久化与恢复；发布后关注失败率、延迟、成本和用户反馈。AI 可以生成代码或测试草案，但需求取舍、正确性标准和是否发布都由我决定。

**考点：** 结果所有权、验收标准、跨层闭环。

**记忆：** “**定义结果、控制过程、验证结果、承担后果**”。

### 14. 需求分析、前后端开发、模型选型调优、工程链路打通，各自的核心动作是什么？

**口述答案：**

| 环节 | 我首先做的动作 | 交付物或验证 |
| --- | --- | --- |
| 需求分析 | 找用户的核心任务、异常情况和成功标准，划清本期范围 | 可复述的用户旅程与验收样例 |
| 后端 | 定义领域状态、接口、不变量和错误语义，再接 Provider/持久化 | 契约测试、关键冲突与恢复测试 |
| 前端 | 把状态和下一步操作呈现清楚，让用户知道系统在问什么、失败后能怎么改 | 交互原型、组件测试、关键旅程 E2E |
| 模型选型与调优 | 先建标注集和规则基线，再比结构化成功率、业务质量、延迟、token 与回退 | 可重复的对照与错误分类，而非只看单条回答 |
| 链路打通 | 跑真实请求，核对跨层字段、状态恢复、超时、幂等和观测日志 | 从输入到结果的完整追踪与故障定位 |

**考点：** 是否能把“全栈”落到每层的可验证动作。

**记忆：** “**需求定目标，后端守合同，前端管交互，模型做评测，集成查链路**”。

## 五、Redis 缓冲 MySQL：吞吐与一致性

### 15. 每秒 5000 次写入，先写 Redis 再异步写 MySQL，你会怎样设计？

**口述答案：** 我先确认业务允许多久的数据延迟、能否丢数据、是否要求单条严格顺序。5000 次/秒约是每分钟 30 万条，Redis 只能吸收短时突发；如果 MySQL 持续只能写 3000 次/秒，积压每分钟增加 12 万条，扩 Redis 也解决不了长期容量问题。若允许最终一致，我会把写入变成持久化消息：入口生成唯一事件 ID，写入可靠队列或 Redis Streams，再由消费者批量、限速写 MySQL；成功提交后才确认消费，失败重试并进入死信处理。MySQL 需要唯一键或幂等更新，按业务键控制顺序，并监控积压量、最老消息年龄和消费延迟。关键业务不允许丢单时，我会优先选择持久消息系统或先写 MySQL 的方案，不把普通 Redis 缓存当作唯一事实来源。

**考点：** 吞吐计算、背压、持久化、幂等、最终一致性。

**记忆：** “**先算 30 万/分钟，再问 MySQL 吞吐；缓冲只能抗峰，不能补长期产能**”。

### 16. Redis 写成功后，进程宕机或 MySQL 写失败，怎么保证两边一致？

**口述答案：** 先明确“一致”是哪一种。如果要请求返回成功时 MySQL 已经提交，就应同步写 MySQL，再用缓存失效或更新机制维护 Redis；Redis 不能充当提前成功的依据。如果业务接受短暂不一致，可以用持久队列做 write-behind：消息在满足持久化要求后才向调用方确认，消费者对 MySQL 幂等写入，数据库提交后才确认消息；重试期间允许重复投递，因此用事件 ID/业务唯一键去重。还要定期对账并补偿漏写。即便用 Redis Streams 和 AOF，也要讨论主从切换、AOF 刷盘策略与故障窗口，不能宣称绝对零丢失。若“Redis 当前值”和“MySQL 最终值”都可被读取，还要规定读哪一边以及版本号如何判断新旧。

**考点：** 强一致与最终一致、ack 时机、至少一次投递、幂等、对账。

**记忆：** “**成功响应点 → 持久化点 → 消费确认点 → 补偿点**”。

**常见追问：** 如果消费者重复处理怎么办？用唯一事件 ID、唯一索引或条件更新；如果同一用户的两笔更新乱序怎么办？按业务键分区/串行处理，并用版本号拒绝旧写；如果队列持续增长怎么办？扩数据库写能力、分片、批量写入或限流，不能只增加缓冲容量。

## 面试前 10 分钟速记

1. **MCP：** 标准化能力接入；Server 适配数据；应用执行权限。
2. **Agent 循环：** 硬预算 + 重复检测 + 业务完成条件；进展必须按任务状态衡量。
3. **架构取舍：** 模型处理开放语义，Harness 处理事实、硬约束和副作用。
4. **16 条评测：** 5 完整 + 5 缺字段 + 3 冲突 + 3 复合语义；两次重复；不能代表真实用户分布，也不证明多轮恢复。
5. **规则重新引入模型：** 复合软目标用 PlanningIntent，语义证据缺口用 Hybrid Retrieval；Verifier 保留最终裁决权。
6. **AI 开发责任：** 自己定义成功标准、审核设计与 diff、组织分层测试和发布门槛。
7. **Redis：** 5000/s = 30 万/min；先算长期吞吐，再谈缓冲；一致性取决于确认和持久化顺序。
