**P0：核心架构**

**Q1：你的项目为什么使用 LangGraph？普通函数调用不行吗？**

推荐回答：

> 普通函数适合线性、一次性流程，而这个项目存在信息补全中断、用户选择、执行确认、局部重规划、外部工具降级和失败补偿。LangGraph 负责管理这些可中断、可恢复、有条件分支的长期业务状态，并通过 Checkpointer 支持任务恢复。

继续追问时补充：

- 简单的 `Router → Planner → Response` 不值得使用 Graph。
- Graph 节点按业务阶段划分，不把每个小函数都画成节点。
- 搜索、评分等细节仍是普通 Service。

记忆思路：

> 函数解决“怎么算”，Graph 解决“进行到哪、接下来去哪”。

------

**Q2：什么是 Agent Harness？它等于 Agent Loop 吗？**

推荐回答：

> Harness 是让模型可靠完成任务的运行环境，包括模型、工具、状态管理、权限控制、持久化、错误恢复和观测评测。Agent Loop 只是 Harness 的一种控制方式，LangGraph 状态图也可以构成 Harness。

项目落点：

> happyFreeTime 使用 LangGraph 作为控制骨架，LLM 负责语义理解，确定性代码负责规划、校验和执行保障。

记忆思路：

> Loop 是发动机运转方式，Harness 是整辆车的控制系统。

------

**Q3：你的项目是 Workflow、Agent 还是 Multi-Agent？**

推荐回答：

> 它是以确定性 Workflow 为骨架、局部使用 Agent 能力的混合系统。RouterExtractor 使用 LLM 理解自然语言，其余规划、校验、权限和执行主要由代码控制。V2 不再把每个模块都包装成 Agent。

为什么不是传统 Multi-Agent：

- Enrichment、Verifier 本质上是确定性服务。
- 多个 LLM Agent 串行会重复理解输入、增加延迟。
- 模块化不等于 Multi-Agent。

记忆思路：

> 看“谁决定下一步”：代码决定是 Workflow，模型动态决定才更接近 Agent。

------

**Q4：LangGraph 中 State、Node 和 Edge 分别是什么？**

推荐回答：

> State 是任务当前的完整业务状态；Node 读取 State、执行业务能力并返回部分状态更新；Edge 根据结构化状态决定下一个节点。

示例：

```
def planner_node(state):
    plans = planner.generate(state["constraints"])
    return {"plans": plans, "stage": "plans_generated"}
```

注意：

> 节点返回的是 State Update，LangGraph 将它合并到完整 State，不要求每次返回所有字段。

------

**Q5：为什么 Graph 的路由由代码决定，而不是让 LLM 输出下一个节点？**

推荐回答：

> LLM 适合判断用户表达了什么，但不适合直接控制权限敏感流程。Router 输出结构化意图，代码根据状态和权限规则决定进入反问、规划还是执行节点。

例如：

```
if decision.need_question:
    return "interrupt"
if authorization.is_valid:
    return "execution"
```

项目原则：

> LLM 理解语义，用户提供授权，代码验证条件，Graph 执行跳转。

**P0：数据与前后端契约**

**Q6：为什么要使用 Pydantic Structured Output？**

推荐回答：

> 节点之间需要稳定的数据契约。Pydantic 可以校验枚举、必填字段、数值范围和嵌套结构，并为 LLM 生成 JSON Schema，避免依赖手动截取和修复 JSON。

项目收益：

- Router 输出错误能立即被发现。
- Graph 路由不会依赖不确定字符串。
- 后端、前端和测试共享清晰契约。
- 模型更换后接口仍保持稳定。

记忆思路：

> Prompt 约束是建议，Schema 校验才是契约。

------

**Q7：Graph State、RunEvent、ResponseEnvelope 有什么区别？**

推荐回答：

> Graph State 是后端内部真实业务状态；RunEvent 是运行过程中通过 SSE 推给前端的进度事件；ResponseEnvelope 是一轮任务结束后的稳定业务响应。

关系：

```
节点执行 → State Update
节点过程 → RunEvent → SSE
最终 State → API 转换 → ResponseEnvelope
ResponseEnvelope → 最后一个 response.completed 事件
```

记忆思路：

> State 给 Graph，Event 给进度条，Response 给最终页面。

------

**Q8：为什么前端不能直接读取 Graph State？**

推荐回答：

> 前端可以消费从 State 提取出的方案和订单，但不应该依赖 Graph 的内部字段。否则 State 重构会直接破坏前端，还可能暴露内部候选、错误、记忆和工具参数。

也不能解析模型文案：

```
// 不可靠
if (reply.includes("三套方案")) showPlans()
```

应该解析结构化事件：

```
if (event.event_type === "plans.ready") {
  showPlans(event.payload.plans)
}
```

------

**Q9：什么是 SSE？为什么不用 WebSocket？**

推荐回答：

> SSE 是基于 HTTP 的服务端单向事件推送，适合前端发起一次 Agent 请求后，后端持续返回阶段进度和最终结果。这个项目主要是服务端向前端推送，所以 SSE 比 WebSocket 更简单。

SSE 适合：

- Graph 节点进度。
- 工具调用状态。
- 模型流式文本。
- 最终结果事件。

WebSocket 更适合：

- 高频双向消息。
- 实时协作。
- 游戏或持续设备通信。

记忆思路：

> 单向持续推送用 SSE，高频双向通信用 WebSocket。

------

**P1：状态恢复与交易可靠性**

**Q10：Checkpointer 是什么？为什么不用普通数据库保存一下就行？**

推荐回答：

> Checkpointer 保存每一步 Graph State 和执行位置，使 Graph 能在 interrupt 或服务重启后从暂停位置继续。普通业务数据库主要保存订单、方案和用户画像等业务事实。

区别：

```
Checkpointer：任务执行到哪里
业务数据库：业务最终产生了什么
```

典型场景：

> Graph 生成方案后暂停等待确认，即使服务重启，也可以根据 `thread_id` 恢复到确认阶段，不重复调用 LLM 和地图服务。

------

**Q11：有 Checkpointer 就能保证不会重复下单吗？**

推荐回答：

> 不能。Checkpoint 和外部写操作之间无法天然形成原子事务。如果下单成功后、保存 Checkpoint 前服务崩溃，恢复时可能重复执行，所以还需要幂等键。

```
idempotency_key = thread_id + action_id + preview_version
```

记忆思路：

> Checkpoint 防止流程丢失，幂等防止副作用重复。

这是很有含金量的追问题，建议重点掌握。

------

**Q12：什么是 Human-in-the-loop？为什么 LLM 判断“确认”后不能直接下单？**

推荐回答：

> Human-in-the-loop 是在高影响操作前暂停流程，由用户提供明确授权。LLM 识别到“帮我订吧”只能触发执行预览，代码还要校验方案、金额、预览版本和用户确认是否一致。

完整流程：

```
选择方案 → 生成执行清单 → 用户确认 → 权限门 → 执行
```

关键点：

> 选择方案不等于确认付费，聊天中的肯定语义也不自动等于有效授权。

------

**Q13：什么是 Saga 补偿？**

推荐回答：

> 多个外部写操作无法使用单个数据库事务时，可以为每个操作定义补偿动作。后续步骤失败后，按相反顺序撤销已完成操作，尽量恢复业务一致性。

```
订票成功 → 订位成功 → 叫车失败
→ 取消订位 → 取消门票
```

注意：

> Saga 不是强一致事务，某些操作可能不可撤销，所以需要记录补偿结果并向用户明确说明。

**P1：规划与外部能力**

**Q14：为什么不直接让大模型生成完整路线？**

推荐回答：

> LLM 擅长理解模糊目标和解释取舍，但不擅长稳定满足时间、预算、营业时间和路线衔接等精确约束。因此模型负责语义层，确定性 Planner 和 Verifier 负责可行性。

分工：

```
LLM：理解用户想要什么
Planner：搜索和组合候选
Verifier：证明方案能否执行
Presenter：解释为什么这样选
```

记忆思路：

> 模型负责“懂”，算法负责“算”，规则负责“守底线”。

------

**Q15：Provider 和降级机制是什么？**

推荐回答：

> Provider 为地图、天气等外部能力定义统一接口。正常使用高德实现；超时、限流或无 Key 时切换到本地估算实现，并在结果中标注数据来源和降级原因。

```
{
  "duration_minutes": 25,
  "source": "local_estimate",
  "is_degraded": true,
  "degraded_reason": "amap_timeout"
}
```

关键点：

- 降级保证主链路可用。
- 估算结果不能冒充实时数据。
- 测试可以使用 Mock Provider。
- 最终候选才调用真实路线 API，控制延迟和配额。

------

**Q16：Beam Search 在项目里解决什么问题？**

推荐回答：

> 多站规划的组合数量会快速增长。Beam Search 每一层只保留评分最高的 K 条部分路线，在穷举和贪心之间取得平衡。

记忆思路：

```
贪心：每次只留 1 条
Beam Search：每次留 K 条
穷举：所有路线都留下
```

项目中先用硬约束剪枝，再根据偏好、距离、预算和差异性评分保留 Top K。

**P1：项目反思题**

**Q17：你的设计有什么不足？**

推荐回答：

> 当前 POI 的动态业务数据仍是 Mock，规划质量依赖人工规则和有限数据；真实路线只对最终候选复核；轻量 Planner 暂时不能覆盖任意复杂多站需求。后续会通过 Beam Search、更多真实 POI、系统化评测和用户反馈闭环继续优化。

好的回答不是声称系统完美，而是说明：

- 哪些是真实能力。
- 哪些是模拟能力。
- 为什么这样取舍。
- 未来接口是否支持替换。

**Q18：你做过哪些架构优化？**

推荐回答：

> 旧版由 IntentAgent、SlotAgent 和 PlannerAgent 多次调用 LLM，存在重复理解和过度反问。V2 将意图识别与约束抽取合并为单次结构化调用，并将时间、位置、天气和默认值移到确定性 Enrichment；Question Gate 只在阻塞字段缺失时中断，规划则交给确定性服务。

面试时最好给量化结果：

```
平均 LLM 调用次数：X → Y
P50 延迟：X → Y
无效反问率：X% → Y%
硬约束通过率：X% → Y%
```

这些数据完成评测后再填，不要预先编造。

**回答方法**

每道架构题尽量按四步回答：

```
1. 结论：我采用了什么
2. 原因：解决什么具体问题
3. 实现：在项目里怎么落地
4. 取舍：它有什么边界
```

例如被问“为什么用 LangGraph”：

> 我用 LangGraph 管理可中断、可恢复的业务状态。因为项目存在信息反问、执行确认和失败补偿，普通线性调用不容易表达这些流程。实现上使用 State、条件边、interrupt 和 SQLite Checkpointer。不过搜索、评分等细节仍放在普通 Service 中，避免 Graph 过度拆分。

这比背“LangGraph 是一个构建有状态 Agent 的框架”有说服力得多。
