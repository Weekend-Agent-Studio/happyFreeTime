## 🧠 已形成的关键认识

- Router 负责自然语言到 `Interpretation`，不负责补默认值或查询业务事实
- Enrichment 区分“用户没说”和“用户说了但没解析成功”
- `user_inferred` 是带用户证据的推断，不属于默认 `Assumption`
- Gate 用确定性业务规则决定是否阻断，不让模型自由决定每次是否反问
- interrupt 保存 Graph 状态，回答恢复后重新经过 Router 以处理自由文本和意图改变
- 离线模式只替换语义抽取适配器，后续 Graph、服务、API 和持久化仍真实运行
- Planning 先保证硬约束可行，再用偏好评分排序；高分不能抵消硬约束违反
- `violation` 属于单个候选，全部候选因 violation 被淘汰后才形成整体 `conflict`；可行方案可以带 `tradeoff` 或非阻断 `warning`
- V2/V1 adapter 是新旧数据契约之间的转换层，不代表从“多 Agent/LLM 规划”切换为确定性规划
- 约束 `source` 回答值从哪里来，`strength` 回答能否违反；两者应正交，当前模型已有前者但尚缺后者
- LLM 适合抽取模糊语义和生成解释，硬约束校验应由可测试的领域规则决定
- 业务表回答“用户拥有什么数据”，checkpoint 回答“工作流运行到哪里”；即使共用一个 SQLite 文件，职责也不同
- `Session` 是长期对话边界，`PlanningRun` 是一次逻辑提交的处理生命周期，`message_id` 不能代替 `run_id`
- `request_id` 应由客户端为逻辑提交生成并在重试时复用，服务端以此避免重复消息、模型调用和方案生成
- `Session Status` 属于稳定业务状态，Graph pending node 属于执行位置；前端通过 `SessionView` 消费产品状态，不读取 checkpoint 内部结构
- 当前后端能按 session 读取消息和方案，但前端没有保留 session 定位或调用恢复接口，因此 M1 的浏览器刷新恢复尚未闭环
- `sessionId` 只是恢复数据的钥匙；后端还必须持久化相应状态并通过 SessionView 返回，不能把 React 内存状态当作业务事实
- 当前 `selectedPlanId` 只表示正在查看；正式 `Selected Plan` 必须由用户确认并写入后端
- `plans` 与 `conflict` 的互斥应由后端契约保证，再由前端判别联合穷尽渲染，不能让 UI 猜测哪个字段可信
- 计划更新期间可以保留上一 Plan Version 并显示运行状态；成功后标记旧版本被替代，失败后明确仍展示上一版本
- 测试通过只证明测试实际经过的边界和写下来的断言，不能自动证明真实数据、真实模型或完整用户旅程
- RouterExtractor 的 Fake 模型测试证明结构化契约、重试和降级，不证明真实自然语言抽取准确率
- 当前 5 条 smoke case 直接运行 Enrichment、Gate 和 Planning，绕过 Router、Graph、HTTP、SQLite 与 React，因此不是端到端测试
- 用户隔离已有 Repository 与 API 测试；刷新恢复尚未端到端实现，也没有浏览器 E2E 证据
- 前端 build 只证明类型检查和生产打包；刷新恢复需要 API、组件和 Playwright 主路径共同提供证据
- GET Session 回归测试应通过公开 HTTP seam 验证消息顺序、完整方案快照和重复读取稳定性，不直接查询数据库，也不把语义不足的 `status=active` 固化为“规划完成”
