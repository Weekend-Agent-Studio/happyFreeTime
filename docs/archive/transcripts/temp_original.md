你的担心非常合理，而且现在正是调整协作方式的好时机。设计阶段需要长上下文和较强推理；实现阶段更适合“小切片、短会话、严格验收”，继续全程使用 Sol + High 往往不是性价比最高的方式。

**1. 模型与智能程度怎么选**

不建议从头到尾固定使用 `GPT-5.6 Sol + High`。

官方定位是：

- `GPT-5.6 Sol`：复杂专业工作和高难度编码。
- `GPT-5.6 Terra`：能力与成本的平衡。
- `GPT-5.6 Luna`：高频、成本敏感任务。
- 官方建议从 `medium` 开始，并在代表性任务上比较相同档位和低一档，而不是默认最高推理强度。[OpenAI 模型指南](https://developers.openai.com/api/docs/guides/latest-model)

我建议采用分级策略：

| 工作                             | 建议配置         |
| -------------------------------- | ---------------- |
| 普通模块实现、补测试、简单接口   | Terra Medium     |
| 明确规格下的机械实现             | Terra Low/Medium |
| 跨模块 Graph、状态机、并发、Saga | Sol High         |
| 疑难 Bug、架构取舍、安全评审     | Sol High         |
| 文档整理、格式修改、测试数据     | Luna/较低推理    |
| 里程碑最终 Review                | Sol High         |

如果 Codex App 没有 Terra/Luna，就继续用 Sol，但把常规开发降到 `medium`。你真正需要保留 High 的地方，是架构契约、复杂状态恢复、执行幂等、失败补偿和最终 Review。

**应该新开会话。** 当前会话承载了大量设计讨论，继续实现会反复消耗历史上下文，也容易让模型被早期设想牵着走。

建议：

- 当前任务保留为“设计档案”。
- 每个 M1/M2 里程碑新开任务。
- 一个任务只完成一个纵向切片。
- 开头只引用三个基线文档和本切片要求，不复述全部历史。
- 完成后生成短 handoff，再开始下一切片。

这通常比维持一个超长实现任务更省资源，也更容易控制范围。

---

**2. 会话应该怎样分工**

我不建议永久维护“设计、实现、评测”三个越来越长的会话。更实用的是：

### A. 设计任务

只负责：

- 需求和架构决策。
- 领域语言。
- 不可逆的取舍。
- 更新架构文档或 ADR。

不要在这里长期写代码。

### B. 每个切片一个实现任务

例如 M1 可以拆成：

1. Pydantic 领域契约。
2. RouterExtractor。
3. Enrichment。
4. NeedQuestion Gate。
5. 最小 Graph 与 interrupt/resume。
6. 最小规划路径。

每个任务都从干净上下文开始，并固定输入：

```text
设计基线：
- docs/grilling_doc/architecture_v2.md
- docs/grilling_doc/v2_gap_analysis.md
- docs/grilling_doc/v2_roadmap.md

本次只实现：
- ...

明确不做：
- ...
- 不为未来需求增加抽象
- 不增加设计文档未要求的 fallback
- 不修改 V1
```

### C. 独立 Review / Eval 任务

实现完成后，开一个新任务审查实际 diff：

- 是否满足规格。
- 是否有 scope creep。
- 是否出现多余抽象和兜底。
- 测试是否验证真实行为。
- 是否需要删代码。

评测不必从第一天拥有一个永久会话。评测集和运行报告应当存在仓库里，任务只是执行和分析它们。官方也把“为 AI 应用添加评测”和“通过评分循环改进困难任务”列为 Codex 的典型工作流。[Codex use cases](https://developers.openai.com/codex/use-cases)

因此更准确的组织方式是：

```text
设计档案任务
    ↓
切片实现任务 1 → 独立 Review
    ↓
切片实现任务 2 → 独立 Review
    ↓
里程碑 Eval 任务
```

**3. 如何减少无用兜底和过度设计**

这不是你的错觉。外部确实有用户反映 Codex 会增加多余层次、假设性 fallback 和未请求的保护逻辑，例如这个公开讨论：[Codex over-engineering 讨论](https://www.reddit.com/r/codex/comments/1ve9nxe/why_does_codex_constantly_overengineer_code_and/)。但目前没有代表性统计，因此只能说明这种体验真实存在，不能说明所有任务都会发生。

产生它的常见原因包括：

- 任务范围太大。
- “要工程化、完整、可扩展”没有边界。
- High reasoning 探索了大量理论风险。
- 模型看见架构文档后试图一次性实现终态。
- 只规定“要做什么”，没有规定“不做什么”。
- 验收标准只要求功能成功，没有要求代码规模和简单性。

### 最有效的约束

每个切片都明确写：

```text
实现约束：
1. 只实现本切片验收标准。
2. 未在测试或设计文档中出现的场景，不增加 fallback。
3. 只存在一个实现时，不创建 Provider/Adapter 抽象。
4. 不为未来功能预留空接口、基类或配置项。
5. 一个 helper 只有在消除真实重复或隐藏复杂规则时才能新增。
6. 新增异常处理必须对应一个已知失败模式和测试。
7. 修改文件超过 N 个或新增代码超过 N 行时，先暂停说明原因。
8. 完成后主动寻找可删除代码。
```

其中第 3 条正好符合 `codebase-design` skill 的原则：“一个 adapter 只是理论接缝，两个 adapter 才证明接缝真实存在。”

### 你的 Skills 有帮助，但不是自动解药

- `tdd`：最有用。它要求一次只实现一个行为，并且“只写足够通过测试的代码”。[Matt Pocock TDD](https://github.com/mattpocock/skills/blob/main/docs/engineering/tdd.md)
- `code-review`：可以检查 `Speculative Generality`、`Middle Man`、`Data Clumps` 等问题。
- `codebase-design`：适用于真正复杂的模块接口，不应每个小函数都用。
- `domain-modeling`：适合定义 Plan、Constraint、Order 等领域概念，不适合普通实现任务。
- `grilling`：设计阶段有价值；需求已经清楚后反复 grilling 会增加流程成本。
- `prototype`：只在状态机或 UI 方案难以靠文档判断时使用。

关键原则是：**Skill 按问题触发，不要每个任务把所有 Skill 串起来。** Skills 本身也可能制造仪式感和额外产物。

建议默认流程：

```text
明确切片
→ TDD 实现
→ 跑测试
→ 独立 code review
→ 删除多余代码
```

**4. 你应该怎样在实现过程中真正学会**

你不需要和 Codex 比打字速度。你的价值应体现在四件事：

1. 定义问题。
2. 做关键决策。
3. 判断实现是否正确。
4. 能解释为什么这样设计。

AI 生成代码不妨碍项目成为你的项目，但前提是你能独立解释、验证和修改它。

### 每个切片采用“预测、实现、复述、破坏”四步

**第一步：预测**

Codex 动手前，你先用自己的话写 5-10 行：

```text
这个模块解决什么问题？
输入是什么？
输出是什么？
最重要的不变量是什么？
最容易出错的两个场景是什么？
我猜会修改哪些文件？
```

不要求完全正确。预测和实际差异正是你学习的地方。

**第二步：实现**

让 Codex 一次只实现一个行为。要求它每完成一个公开接口后停下来说明：

- 新增了什么。
- 为什么需要。
- 测试证明了什么。
- 哪些情况刻意没有处理。

**第三步：复述**

不要直接问“给我解释代码”。你先解释给 Codex听：

> 我理解 RouterExtractor 只抽取原文，Enrichment 才负责默认值，因此天气不能注入 Router Prompt。我的理解对吗？

让 Codex纠错，比被动阅读讲解更有效。

**第四步：破坏**

你亲自做一件小实验：

- 改掉一个默认值，观察哪条测试失败。
- 删除一段校验，确认测试是否能发现。
- 构造一个严格预算缺金额的输入。
- 让高德 Provider 超时，观察降级路径。
- 重复提交确认请求，检查幂等。

能把系统弄坏再修回来，才算真正理解。

### 建立“面试证据账本”

每完成一个切片，记录：

```markdown
## RouterExtractor

问题：
旧链路为什么慢？

我的决策：
为什么合并 Intent 和 Slot？
为什么不让 Router 调工具？

被否决方案：
为什么不用自由 ReAct Loop？
为什么不把天气注入 Prompt？

核心不变量：
Router 不创造默认值。
每个抽取字段保留 evidence。
解析失败不能伪装成 chitchat。

验证：
哪些测试覆盖了这些不变量？

指标：
LLM 调用数从多少降到多少？
P95 延迟变化多少？

一次真实问题：
遇到什么 Bug，我如何定位和修复？
```

到写简历时，这些就是素材，不必凭记忆编故事。

### 每个里程碑做一次口头答辩

让 Codex扮演面试官，连续追问：

- 为什么用 LangGraph，不用单 Agent loop？
- Router 和 Enrichment 为什么分开？
- 默认值错误怎么办？
- 为什么 Provider 不先做 MCP？
- Graph checkpoint 和订单数据库谁是真相源？
- 部分预订成功后如何补偿？
- 评测为什么不要求命中唯一 POI？

你先回答，Codex只负责指出漏洞，不替你生成标准答案。连续两次能在不看文档的情况下说清楚，才算掌握。

### 面试中如何体现你的价值

不要说：

> 我用 Codex 完成了一个周末规划 Agent。

应该说：

> 我把原本多轮 Intent、Slot、Planner Agent 链路重构为一次结构化语义抽取与确定性补全，将 LLM 从事实查询和业务决策中移出；规划使用硬约束剪枝、可解释评分和真实路线复核，执行侧通过确认快照、幂等键和 Saga 管理部分失败。随后用固定评测集比较重构前后的成功率、反问率和延迟。

这句话体现的是你的系统判断，而不是代码由谁敲出来。

**我对你最实际的建议是：M1 先继续使用 Sol High 完成第一条正确的纵向样板；样板稳定后，普通切片切到 Terra Medium，并为每个切片新开短任务。每次要求测试先行、限制 diff、禁止假设性 fallback，里程碑末尾再用 Sol High 做独立 Review。**这样质量下降通常很小，但资源消耗和过度设计都会更可控。
