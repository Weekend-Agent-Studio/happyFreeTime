# S-AB1 Pilot Status — Legacy Multi-Agent vs Resume V2

The first bounded S-AB1 pilot is complete on experiment branch `codex/s-ab1-v1-v2`.

Compared revisions:

- Legacy Multi-Agent: `develop@90639f3`
- Resume V2: `planner-v2-eval-baseline` / `bef5fa3`

Six reviewed common cases were executed with a read-only legacy adapter and the existing V2 evaluation runner. Modification cases were excluded because the legacy graph has no equivalent structured replacement action.

Results:

- Legacy: `1/6` expectations. Five cases stopped in the legacy `SlotAgent` before planning because its broad required-slot gate requested budget or date. One unknown-date case correctly asked for the date.
- V2 B0: `5/6`, required assertions `21/23`, hard-constraint safety `3/3`, conflict diagnosis `1/1`, P50/P95 `1369/1857 ms`.
- V2 B3: `5/6`, required assertions `21/23`, hard-constraint safety `3/3`, Advisor acceptance `3/3`, P50/P95 `1838/6023 ms`.

The B3 pilot had three retrieval fallbacks because the BGE index was unavailable in that environment, so it is diagnostic only. The V2 failure in both pilots was `clarify_unknown_date`: the frozen input reached planning instead of the reviewed date clarification and needs a fixture/path audit.

These numbers are not final architecture uplift metrics. The legacy system often terminates before its PlannerAgent, while V2 can continue with defaults and deterministic fallback. A formal comparison must explicitly choose either:

1. a product-level comparison that reports this early-stop behavior as a capability difference; or
2. a controlled planner-core comparison that supplies the legacy agent's required slots from the same reviewed fixture.

No baseline source was modified; the adapter injects only a deterministic weather stub for the legacy app's missing external MCP dependency. Raw model outputs and secrets were not saved.
