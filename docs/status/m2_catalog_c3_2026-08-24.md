# M2 Catalog C3：轻量、可重建的 POI 数据链路

_状态快照 · 2026-08-24_

## 用户故事与验收结果

作为规划用户，我希望系统默认使用一批来源可说明、可离线重建的北京 POI；数据缺失时明确显示“未知/待确认”，而不是把 Mock 当成真实事实，使规划结果既有可展示的内容，也不伪造可靠性。

- 版本化 Overpass 查询可在线采集，也可从仓库内 raw response 完全离线 replay。
- `pois.json` 固定产出 200 个唯一资源，活动与餐饮各 100；同一 OSM 对象被多条查询命中时只保留一次。
- OSM 的 Wikidata/Wikimedia Commons 引用解析为许可可追溯的远程图片；图片失败不影响规划，UI 使用类别占位图。
- 缺营业时间或儿童适配信息时不填 Mock、不直接淘汰，而是对最终方案输出 `CatalogWarning`；已知硬约束违反仍输出 `ConstraintViolation` 并剪枝。
- 旧 M1 JSON 位于 `data/fixtures/v1/`，只作为显式测试/兼容 Fixture；默认 `SnapshotCatalog` 不读取它们。
- 旧 36 行 CSV 和 `CsvCatalog` 已移除，避免两套静态格式及逐字段 provenance 增加维护负担。

## 数据链路

```text
versioned *.overpassql
  -> public Overpass responses (data/catalog/raw)
  -> OSM type/id 去重与活动/餐饮平衡选择
  -> versioned Commons metadata replay
  -> deterministic pois.json + completeness.md
  -> SnapshotCatalog (WGS84 -> GCJ-02)
  -> Catalog hard pruning + unknown warnings
  -> Planning finalists
  -> FastAPI / React source, warning, image or category placeholder
```

来源契约保持在资源级：`source_name`、对象 URI、许可、采集时间和核验状态。项目派生的类别、天气敏感性和建议停留时长不再用多个字段列表制造“很精细”的错觉；这些值仍不是现场核验事实。

## 明确不做与限制

- 不抓取大众点评，不绕过登录、反爬或许可限制；也不把高德 POI 响应批量提交为项目数据库。
- 不随机补价格、地址、营业时间、亲子适配或图片。当前严格预算无法由这批 OSM 数据证明时会如实无解。
- 不下载或永久保存图片文件；餐饮图片覆盖仍低，类别占位是正常降级。
- 基础营业时段不是实时营业保证；当前 D0 已按实际到达/停留时间复核同日基础时段，并保留 10 条多区间记录，但节假日、跨夜规则和临时闭店仍未覆盖。
- 当前仍是双站 V1 组合兼容层；C3 没有实现 3/4 站、多策略多样性、动态库存或完整 Verifier，M2 不标记完成。

- `tests/test_planning.py`：snapshot 离线进入双站组合；只把最终 Stop 的待确认项公开。

- 严格 msgpack 后端全量回归 `64/64`、离线 smoke `5/5`、前端 `pnpm run build` 通过；它们不是浏览器 E2E，也不证明 POI 当前营业或价格准确。
